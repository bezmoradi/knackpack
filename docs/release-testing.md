# Release testing

What each knackpack release from 0.26.0 to 0.40.0 was tested with and what that testing left out, oldest first, moved here from the README's [Limitations](../README.md#limitations).

- Committed documents and the fix for messages sent as a turn ends are new in 0.26.0. The mode ran in six headless runs with Bash on 2026-11-13 (Claude Code 2.1.323, `claude-opus-5-5`, $3.49 in all), on an eval fixture with staged and unstaged work of its own. With `KNACKPACK_DOCS` unset, Challenge requirements and Plan implementation changed neither the working tree nor `HEAD`. With it set, the brief, the plan and a revision of the plan each became a commit of only their own files, `feature.json` named the brief's folder, no committed copy named a path from the machine, and the other work stayed as it was. Outside a git repository, Claude said the brief wasn't committed and gave the scratch copy's path. After an outside review changed how the script commits, three runs of the final version the same day ($1.73) agreed: the brief and then the plan became commits titled `docs(knackpack): requirements for <task>` and `docs(knackpack): plan for <task>`, changing only the document and `feature.json`, with the staged, unstaged and untracked work left as it was, and in a repository whose pre-commit hook runs `git add -u`, the script took its commit back and printed `not committed`, leaving `HEAD`, the index and the other work unchanged, and Claude said why and gave the scratch copy's path. Execute plan and Handoff haven't run with the mode on, and the fix for messages sent as a turn ends is checked only by `scripts/check.sh`, since a headless run can't send a message while a turn is ending.
- The compaction focus is new in 0.26.0. In a headless run on 2026-11-13 (Claude Code 2.1.323, Haiku 5.5, about $0.01), Claude Code ran `hooks/compact.sh` from the plugin before a `/compact`, and the summary's own notes named "the knackpack additional instructions on preserving command results, diagnoses, decisions, file paths, and any questions or numbered options". An earlier run that day, with a stand-in hook, showed a hook's instructions adding to those from `/compact` and a "Compact instructions" section in `CLAUDE.md`: the summary kept the word each of the three asked for. How much the focus improves what Claude recalls after a compaction hasn't been measured for knackpack, and automatic and idle compaction weren't run, though Claude Code's documentation says the hook runs for both.
- Checkpointing without a paste is new in 0.26.0. It ran headless on 2026-11-13 (Claude Code 2.1.323, `claude-opus-5-5`, $5.27 with one run whose harness denied the checkpoint's folder): a short review, `/knackpack:checkpoint`, `/compact`, then "ok, fix number 2". The checkpoint reply led with running `/compact` and then sending the next message, with the paste as the fallback. After the compaction, the session-start hook's pointer and the summary's "First, read … `CHECKPOINT.md` in full", which the compaction focus asked for, were both in the new context. Claude Code also re-reads up to five recently used files after compacting, each only if under 5,000 tokens: a 2.5 KB checkpoint came back whole that way, so Claude didn't read it again, and a 51 KB one came back as a path only, which Claude read in full before anything else. With intent tracking off, only the compaction focus points to the file, and that wasn't run.
- Execute plan's commit procedure is new in 0.26.0 and hasn't run live. Its git steps were checked by hand with git 2.49.0: committing by path, adding new files first, keeping your staged and unstaged edits out, undoing a commit that a hook running `git add -u` filled with other work, and unstaging new files after a hook rejects a commit. Whether Claude follows the procedure when it commits packages is untested.
- `scripts/commit-docs.sh`'s refusal when the repository's own settings set `KNACKPACK_DOCS` is new in 0.26.0, and only `scripts/check.sh` has run it: in a throwaway repository, a tracked `.claude/settings.local.json`, a committed `.claude/settings.json`, or a committed `sub/.claude/settings.json` spelling the name with a `\u` escape makes it refuse and leave `HEAD`, the status and `feature.json` as they were, and the session-start hook then prints its note instead of the rules; an untracked local file still lets it commit. No live session has run with a repository's settings setting the variable.
- The prompt audit before a push, `scripts/prompt-audit.sh`, is new in 0.27.0. On 2026-11-13 (Claude Code 2.1.325, `claude-opus-5-5`), from a Claude Code session in a throwaway clone pushing to a local bare repository, it stopped the push of a skill with three planted defects, an all-caps "think step by step" line, a step running a script that doesn't exist and a step contradicting the skill's own rule against committing, and reported all three at high confidence. It skipped an agent changed only in its copy of the review protocol, passed this release's own fixes, and stopped the push when the claude-api skill was off and when the budget ran out. Each audit cost $1.07 to $1.31 and took about a minute and a half; a $0.02 cap still spent $0.63. Two audits of the same file reported different findings, which is why a file version's result is kept and not rerun. Auditing all 33 of 0.26.0's instruction files one at a time, for about $39, reported 1 high-confidence finding, 37 medium and 61 low. This release applies each where the repository or a primary source bears it out, and otherwise leaves the text as it was, with the reason recorded. The evals of every changed skill and agent then ran on this release and on 0.26.0, with `claude-opus-5-5` and a Haiku judge, and without Bash, which that machine can't grant evals, so they don't show how the reviewers behave when they can run commands. One case got worse: the TypeScript reviewer graded a defect in old code that the change newly calls as the change's own High finding, and its instructions now say such a defect stays a pre-existing issue.
- The field-report fixes are new in 0.28.0. The intent hook's note for subagent hand-backs, its ignoring of staging, and its new order for shortening a long record ran in `scripts/check.sh` under dash, macOS `sh` and bash, whose new checks fail on 0.27.0's hook, and in the `quick` and `intent` evals on 2026-11-13 (Claude Code 2.1.325, `claude-opus-5-5`, Haiku judge, $3.07), where every case passed with the plugin. The protocol's new rules on the shell, local requests, downloaded tools, skipped checks and the Cost line without a shell haven't run in a reviewer eval.
- 0.28.1 fixes that note, which 0.28.0 didn't print for real hand-backs: Claude Code gives the hook a hand-back as a prompt starting with `<agent-message`, while the transcript shows it after a line "Another Claude session sent a message:", the only form 0.28.0 matched. In a live session on 0.28.0 on 2026-11-14 (Claude Code 2.1.322), three hand-backs got the full reminder, each queued prompt starting with `<agent-message`. The fix accepts either form and runs in `scripts/check.sh`, and in a live session on 0.28.1 the same day and version, a hand-back got the short note.
- 0.29.0 has reviewers mark where one command's output ends with a separator such as `echo ---`, which works unquoted in every shell, instead of a quoted `echo '===='`. Reviewers on 0.28.1 still wrote it unquoted, and zsh, which reads a word starting with `=` as a command lookup, failed and ran nothing after it: 7 times in 5 of 6 live security reviews in one session on 2026-11-14, mostly while joining instruction files at step 5, once while joining parts of ordinary files. So step 5 now also has them read each instruction file on its own, with the Read tool or one `git show` per command, and the new separator covers every other joined command. The shell paragraph also says macOS's `head` refuses `-0`, which a review used to discard output. 0.29.0 also has Challenge requirements, which knackpack starts before every change, hand building from a plan to Execute plan rather than make the change, and Execute plan's description names a phase of a plan, PRD or roadmap: in a live session on 2026-11-14, a request to start a roadmap's Phase 0 went through Challenge requirements, whose rules said it "then makes the change", and the main session built the phase without subagents, while the same kind of request in another session started Execute plan, which handed each package to one. That changes what the challenge hook prints, so it's a MINOR release. `scripts/check.sh` checks the hand-off and fails without it. No reviewer, challenge or trigger eval has run on this wording, and no eval case sends a plan go-ahead with the challenge rules on.
- 0.29.1 tells the adversarial, security and architecture reviewers that the adjudicator is the only agent they ever start. Before, their instructions ruled out other agents only for adjudication, and in a live session on 2026-11-12 an adversarial review started four forks to split its review. `scripts/check.sh` now checks that each agent with the `Agent` tool says so, and fails on 0.29.0's agents. The reviewer evals haven't run on this wording yet.
- 0.29.2 corrects the protocol's advice on globs. It said to quote globs in a one-line command, which a reviewer can't do with a glob it wants expanded, so reviews wrote them unquoted with `2>/dev/null` added, as in `wc -l store.go pack*.go 2>/dev/null`. zsh refuses to run a command whose glob matches nothing, with `no matches found`, before the redirect can hide it; this happened 3 times in live reviews on 2026-11-14, once on 0.29.1. The protocol now says so, and has reviewers find files that may not exist with `find <folder> -name '<pattern>'`, which prints nothing when none match, in every shell. 0.29.2 also has reviewers keep their four-line reply, ending with the findings line and the `knackpack-verdict/1:` line, even when their brief asks for only the report's path: in a live session on 2026-11-14 on 0.29.1, given briefs ending "reply with only its path", four of the first ten reviewers to reply gave the path alone, so a program reading verdicts would have found none, and six kept all four lines, where all 25 reviewer replies on one machine since the verdict line came in had had it. The reviewer evals haven't run on this wording.
- 0.30.0 sends a request to build what a plan, PRD or roadmap describes, such as a phase or a section, with or without work packages, straight to Execute plan instead of Challenge requirements. 0.29.0 had Challenge requirements hand such work over, but in a live session on 2026-11-14 on 0.29.2, a request to build the tables a PRD section describes started Challenge requirements, and the main session then changed the model, validation, runner, diff and report itself, with no subagent. Replayed headless in a throwaway copy of that project, on 0.29.2 and on a version that only widened the hand-off's wording to sections without packages, all three runs did the same once given the go-ahead, including "Implement prd.md §11.3 (tables)…": once in Challenge requirements, the session builds. The challenge hook's rules now route that request to Execute plan, which opens with a short challenge of its own, asks only blocking questions, records minor choices as assumptions, and cuts packages by the components they change when the document has none. On this version, the two table requests each started Execute plan within five seconds, one followed further handed the table package to an implementation subagent with no edit in the main session, and an ordinary small change still started Challenge requirements (Claude Code 2.1.325, `claude-opus-5-5`, about $5 in all). That changes what the challenge hook prints, so it's a MINOR release. To stay under its size limit, Challenge requirements drops its note that a long document is better passed as a path than pasted. `scripts/check.sh` checks the routing and fails on 0.29.2's wording. No trigger, challenge or plan-execution eval has run, and each case ran once.
- 0.31.0 has the intent hook say how to fix a proposal whose status it can't read, instead of only naming it. A proposal's status follows its attribution, as in ", by Claude. open", and the hook lists the open ones. On one machine by 2026-11-14, 13 sessions had got the old notice, and in the two still running the entries stayed unreadable: one got it with 604 of its messages, for two entries saying "closed as out of date; replaced by REQ-56 to REQ-66", a status the hook doesn't know, written before one it does; another wrote "By Claude. (1)-(3) accepted as REQ-65", a partial acceptance with nothing after the attribution. The notice now asks Claude to fix each in the same turn, keeping its meaning: the status first, then any note, and a part still undecided as a new open proposal. Headless, in throwaway repositories holding both kinds of entry, a question that changes nothing left them as they were on 0.30.0 and had them fixed on this version, the undecided parts listed as two new open proposals and a "Noted:" line saying so (Claude Code 2.1.325, `claude-opus-5-5`, one run each, $0.62). 0.31.0 also stops the turn-end check from reporting a record update as missing when it happened before a subagent's hand-back. A hand-back or a background task's notice starts a new turn, and the check compared the record only with how that turn found it, so a reply after a hand-back ending with "Noted:" for an update made in the turn of the developer's message was told the record wasn't updated. On one machine by 2026-11-14, that notice appeared five times, four in turns a hand-back or background task started, each after the record had changed since the developer's message, and the sessions then spent a turn confirming the record was right. Such a turn now keeps the starting point of the turn before it, so the check reads changes since the developer's message, and a claim with no change since then is still caught. That changes what the intent hook prints, so it's a MINOR release. `scripts/check.sh` checks the notice and both cases after a hand-back; the notice and the update made before a hand-back fail on 0.30.0's hook. The `intent` evals haven't run on either change.
- 0.31.0 also has the checkpoint's reply tell you to wait for the compaction to finish before sending your next message, since Claude Code holds a command typed during a reply but delivers a message into the running turn: in a live session on 2026-11-15, a message typed right after `/compact`, while the checkpoint was still being written, reached Claude first, and the compaction ran after Claude had worked on it in a context of about 472k tokens. The reply also no longer depends on Claude knowing whether you typed `/compact` already, which it can't see. No checkpoint eval has run on this wording.
- 0.32.0 adds, for programs that run the reviewers, the reviewer catalog, `agents/catalog.json` in the `knackpack-catalog/1` format, so a program choosing reviewers doesn't have to copy Orchestrate review's rules, and a `knackpack-finding/1` line per row of each reviewer's findings table, before the findings line, so it gets each finding without parsing the report (see [Reading knackpack from a tool](../README.md#reading-knackpack-from-a-tool)). The findings and verdict lines don't change, and win when a finding line contradicts them. The count command prints the finding lines from the same table it counts, so they can't disagree with the counts, and the reply is no longer a fixed four lines. `scripts/check.sh` runs that command on sample tables, and checks the catalog against the agent files and Orchestrate review's rules. Both add to the public interface, so it's a MINOR release. Headless, on a throwaway Go repository whose change builds SQL from user input and drops scan errors, the Go, security, adversarial and slop reviewers each ended their reply with one finding line per table row, 5, 2, 2 and 2, matching each row's ID, severity, blocking, path and line, then the findings line and the verdict line, and the slop reviewer on a change that only rewords the README printed no finding lines and `knackpack-verdict/1: pass` (Claude Code 2.1.325, `claude-opus-5-5`, one run each, $4.47). In the `quick` evals ($2.36, Haiku judge), two cases passed all six runs, and the regex case's `gives-a-regex` grader failed all six, with and without the plugin, as in earlier runs. No other reviewer eval has run on this version.
- 0.32.1 makes the protocol's advice on literal globs concrete. It said to quote a glob meant literally, and reviewers didn't read every such word as a glob: from 0.29.2 to 0.31.0, security reviewers in live sessions on one machine hit zsh's `no matches found` 15 times by 2026-11-15, 11 of them an unquoted `grep -r --include=*.go` or another extension, 1 a requirement ID written as `V13.4.?` in a `for` list, and 3 globs for files that didn't exist, which the `find` advice already covers. The shell paragraph now names `*`, `?` and `[` and gives `--include`, such an ID and a URL with a query as examples. `scripts/check.sh` checks the wording; no reviewer eval has run on it.
- 0.32.2 has Plan implementation say that its plan's folder belongs to the session and the operating system may clean it up, so copy the plan somewhere durable, as Challenge requirements and Research already say of their briefs; only `scripts/check.sh` has run on it. Execute plan is unchanged: headless on 0.32.1, in a throwaway repository with a plan that stopped partway (Claude Code 2.1.325, `claude-opus-5-5`), it left the finished package alone and built on the half-done one in 4 of 4 runs, and when asked to commit, it committed the half-done package's file with only that package's files in 2 of 2 ($4.52 in all).
- 0.33.0 keeps how you asked the work to be done in front of Claude (see *How you asked the work to be done* under [Track intent](../README.md#track-intent)), after a field report on 0.32.2 ([#77](https://github.com/bezmoradi/knackpack/issues/77)) showed sessions, after compacting, implementing a plan directly instead of handing it to subagents as asked, and not reading the checkpoint the session-start hook pointed to. Checkpoint and the compaction focus keep the way of working too, and Track intent names "subagents implement" as an example of one. The hooks print more than before, so this is a minor version. `scripts/check.sh` tests the reminder under dash, sh and bash. In one headless run on 2026-11-16 (Claude Code 2.1.326, `claude-opus-5-5`, about $6 in all), a throwaway session recorded "you orchestrate and subagents implement" on the Status line, saved a checkpoint, ran `/compact`, then got "ok go ahead": the reminder came with that message, Claude started Execute plan, and subagents made both code edits. Claude Code had re-attached the 2.6 KB checkpoint itself, so Claude didn't read it again. That was one run with no run of 0.32.2 beside it, so how much this changes what Claude does isn't measured. The `intent` cases passed 3 of 3 on this version and 3 of 3 and 1 of 3 on 0.32.2 (same model, `sonnet` judge), where the what-if case's judge varies from run to run. No eval covers a compaction, and the `trigger` cases, which don't turn intent tracking on, didn't run. When a message itself sets off an automatic compaction, it isn't known whether the reminder comes with that message or the next one.
- 0.33.1 adds eval graders that fail when a reviewer's reply leaves out the lines a push gate reads. Session logs on one machine showed that in a live session on 0.29.0, 6 of the 14 reviewers that finished ended their reply with the report's path instead of `knackpack-verdict/1:`, and the API stopped 7 more with a refusal before they replied; one reply on 0.29.1 had no `knackpack-findings/1:` line. No later run has left either line out, but no grader read them, so nothing would have caught it again. In `reviewer-finds-planted-defect` and `reviewer-accepts-correct-code`, `reply-ends-with-verdict` now requires the findings line followed by the verdict line, with only blank lines after it, and `no-pass-over-blocking` fails a findings line that counts a blocking finding directly above `knackpack-verdict/1: pass`; in `adjudicator-fix-locks-out-owner`, `reply-ends-with-verdict` requires the verdict line on its own line at the end of the reply. They read the run's trace, which holds the agent's reply as the Agent tool's result and as a task notification. `reply-ends-with-verdict` is `arm: with-only`, so a two-arm run reports it without scoring it; `no-pass-over-blocking` guards both arms. On 2026-11-17 the three cases ran once each with `--ablation none` and without Bash (Claude Code 2.1.326, `claude-opus-5-5`, `sonnet` judge, $1.54 in all) and passed every grader. The check that nothing follows the verdict line came after that run, from its review, and was tested only on its traces: they still pass, the new graders fail with the lines deleted or a path put after the verdict line, and the guard fails with a blocking count put above `pass`. The suite still has 213 cases.
- 0.34.0 gives each `llm` grader one question, as `.claude/CLAUDE.md` now asks. The `intent-what-if-changes-nothing` case's `answers-the-what-if` grader asked four things at once: an answer, that support would see other organizations' orders, that this is the user's decision rather than something that just works or breaks, and no claim of a change, agreement or record. In a two-arm run on 0.33.0 on 2026-11-16 (Claude Code 2.1.326, `claude-opus-5-5`, `sonnet` judge), it failed both arms' replies, which were both right: nothing would break because every user already sees every organization's orders, support included. Split to ask only whether the reply said support would see other organizations' orders, it still failed 1 of 3 runs on 2026-11-17 ($0.78), a correct reply that said so only through its headings, since the question already supposes it. So it now asks whether the reply answers what would happen from what app.py does today, with nothing breaking, because everyone already sees every order, as a correct answer; a new `no-support-role-claim` grader asks whether the reply claims app.py already has a support role, and the `tool_used` and `regex` graders still check that nothing was edited or recorded. Reworded, it passed 3 of 3 runs on 2026-11-17 with every judge voting PASS ($0.79), where before the judges split; three runs can't show it never misjudges, and no run tested a reply that should fail it. The case now has four graders, so its scores aren't comparable with earlier runs.
- 0.34.0 also adds the opt-in gate before `/compact` described under [Compaction focus](../README.md#compaction-focus) ([#79](https://github.com/bezmoradi/knackpack/issues/79)). `scripts/check.sh` tests it under dash, sh and bash: no checkpoint, one newer and one older than the last compaction, a checkpoint in the scratchpad and in the temporary folder, the skip word, automatic compaction, headless runs, input with no session ID, and a marker folder that is a symbolic link. On 2026-11-17 (Claude Code 2.1.326, `claude-opus-5-5`, $0.69), two headless `/compact`s in a throwaway session with the gate on compacted and wrote no marker, the second with `CLAUDE_CODE_SESSION_ATTENDED=1` set by the caller, which Claude Code replaced, and knackpack's summary instructions reached both summaries. So the stopping path has run only under `scripts/check.sh`, not in an interactive session, where the hooks reference says Claude Code shows a stopped manual `/compact`'s message from stderr.
- 0.35.0 makes reviewers check claims themselves and adds a line per requirement for programs that read replies ([#83](https://github.com/bezmoradi/knackpack/issues/83)), both in the shared review protocol. A claim about the code from a commit message, a pull request description, a comment, the brief or another agent's report is now something to check: before a finding, a pass or a verified requirement relies on a fact, the reviewer quotes the lines it rests on with their `path:line`; a claim it couldn't check is reported as not verified and is never why the change passes; and it reads code itself, not through another agent. A reviewer given requirements with IDs adds a requirements coverage table, from which the count command prints a `knackpack-coverage/1` line per ID, before the finding lines (see [Reading knackpack from a tool](../README.md#reading-knackpack-from-a-tool)). The finding, findings and verdict lines don't change, and a reply without requirement IDs is as before, so it's additive and a MINOR release. `scripts/check.sh` runs the count command on sample coverage tables, including ones it must refuse. Two eval cases are new, `reviewer-comment-claims-tested` and `reviewer-reports-requirement-coverage`, making 215. On 2026-11-18 (Claude Code 2.1.327, `claude-opus-5-5`, `sonnet` judge, plugin only), Claude Code refused Bash to every eval on the test machine, whose SSH config uses a shell expansion it can't resolve, so `reviewer-comment-claims-tested`, `reviewer-finds-planted-defect` and `reviewer-accepts-correct-code` ran once each without it ($1.69) and passed every grader: in the first, the reviewer quoted the comment, reported its claim as a confirmed Low finding, since the test file it names doesn't exist, and passed the helper on its own reading. The coverage case needs Bash for the count command, so its fixture ran once headless with `--plugin-dir .` and Bash allowed ($0.92): the reply ended with REQ-01 verified at `app/orders.py:24` and REQ-02 violated at `app/orders.py:25`, then the finding line, the findings line and `knackpack-verdict/1: block`, and the case's five regex graders pass on its transcript. No run compared either new case with Claude alone, and none of the other 50 reviewer cases ran on this version.
- 0.36.0 adds the code health reviewer, `code-health-reviewer` ([#85](https://github.com/bezmoradi/knackpack/issues/85)), a report-only agent that assesses where a whole code base or subsystem is costly or risky to change and compares that with an earlier revision (see [Reviewers](../README.md#reviewers)). It's a new agent and changes no existing name, line or path, so it isn't a breaking change and is a MINOR release. Its catalog entry is the first with `canBlock: false`, since its verdict line is always `pass`, so a program that reads `canBlock` should stop assuming every reviewer can block (see [Reading knackpack from a tool](../README.md#reading-knackpack-from-a-tool)). `scripts/check.sh` now checks that each recipe block in an agent file hashes to the `sha256=` on its fence line, and that the snapshot example parses with the keys the agent defines, schema version 1 and those digests, and shows the check failing on a copy with one byte of a block changed and on one with a digest changed. Before the agent was written, its recipes ran in a spike on throwaway clones of two private repositories, one Go and TypeScript and one multi-module Go, a shallow clone, a copy of the Python 3.14 standard library (1,855 files), and small repositories of its own with spaces and non-ASCII characters in paths, symlinks and a submodule entry; two runs on each gave the same output byte for byte, also under dash and with a different git configuration. On 2026-11-19 the agent ran live twice, headless, on a throwaway clone of a Go and TypeScript repository of 669 files and 68 commits, as the code health cost bullet in the README's [Limitations](../README.md#limitations) details, and the compare run reported all 7 of the assess run's findings unchanged, none new and none fixed. The same day, `claude plugin eval` wouldn't run cases that grant Bash on the test machine, so its 12 new eval cases ran by hand with the plugin only (see [Local Development](../README.md#local-development)); they still need a run with `claude plugin eval` to compare them with Claude alone.
