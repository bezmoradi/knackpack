# Working on knackpack

knackpack is a Claude Code plugin made of Markdown plus four hook scripts: skills in `skills/<name>/SKILL.md`, agents in `agents/<name>.md`, hooks in `hooks/` that load the track-intent skill and check that its record stays up to date, that print the challenge rules at session start, that warn when the context grows large, and that keep the software factory page, the pre-publish checks in `scripts/check.sh`, which CI runs on Linux and macOS, and behavior evals in `evals/` for `claude plugin eval`. The repository root is both the plugin and its marketplace, so every file at the root ships to every user. The README's Local Development section has the commands; this file holds the rules.

## Rules

- **Edit the review protocol in one place.** All fifteen agent files end with the same "Review protocol" section, copied from `scripts/review-protocol.md`. Edit that file and run `sh scripts/sync-protocol.sh`; never edit an agent's copy, which `scripts/check.sh` reports.
- **Keep each agent's instructions in its own file.** Don't move rules into files an agent reads while it works: a plugin's files sit outside the user's project, so reading them needs permission, which Manual mode asks for and headless runs deny, and the rules would silently go missing. That includes the name of the file an agent saves its report to (`<name>.md`): a subagent never sees its own frontmatter, so its instructions have to name the file, and the review protocol asks for the name they give.
- **Keep the agents report-only.** Every agent lists its tools in `tools:` and never gets Edit, Write or NotebookEdit. Only the adversarial, security and architecture reviewers get `Agent`, and they use it only to start `knackpack:adjudicator`; Claude Code ignores a type list such as `Agent(knackpack:adjudicator)` in a subagent's `tools`, so only their instructions hold them to that. Keep `omitClaudeMd: true` on every agent.
- **Write everything yourself.** Don't copy text from other projects, even MIT-licensed ones, and don't include the text of ASVS requirements or of the other OWASP sources the security reviewer uses, which are licensed CC BY-SA; the reviewer downloads them at pinned commits instead, and checks the ASVS file's checksum. Their IDs, titles and file names are fine.
- **Keep it generic.** No company or product names from private projects, no email addresses, and no names of private repositories.
- **Check facts against primary sources:** the Claude Code docs, specs, RFCs and library source. Name the version when behavior changed in one.
- **Keep the skills in the Agent Skills format, with Claude Code's keys.** The skills use the [Agent Skills](https://agentskills.io/specification) folder format inside a Claude Code plugin, and their workflows need Claude Code's agents, hooks and variables, so nothing promises they work in other products. Say which kind of rule a change rests on. The format requires a `name` of 1 to 64 lowercase letters, digits and single hyphens between them, matching the folder, and a `description` of at most 1,024 characters, and caps `compatibility` at 500. Its documentation's advice, such as a body under 500 lines or files loaded on demand, is advice, not a requirement. Knackpack's own policy is one-line frontmatter values and Claude Code's keys `argument-hint` and `disable-model-invocation`. Keep those keys even though the format's validator, claude.ai uploads and the Skills API reject them: without `disable-model-invocation`, Claude could start on its own two skills meant to start only on request, and the track-intent skill the hook already loads. `scripts/check.sh` checks all of this, since `claude plugin validate` checks only that a description exists.
- **Keep each `SKILL.md` under about 19,000 characters.** After compaction, Claude Code carries over only the first 5,000 tokens of each skill, and no more than 25,000 tokens across all the skills the session invoked, newest first, so an older skill can drop out entirely. Anything past those limits is lost, so put rules Claude must keep, such as where a skill saves its files, near the top. Keep track-intent's body under about 8,500: the hook prints it along with the session's paths, and Claude Code cuts hook output past 10,000 characters to a short preview, so past 9,900 bytes the hook prints only a pointer to the skill file, which Claude then has to read itself.
- **Keep the hooks safe for every user.** `hooks/track-intent.sh` runs at every session start, message, file edit and turn end for everyone who installs knackpack, `hooks/challenge.sh` at every session start, `hooks/context.sh` at every message, and `hooks/factory.sh` at every session event and tool call, though it only checks a marker file until the user turns it on; the rules below hold for all four, and `challenge.sh` and `context.sh` write nothing at all. Keep it POSIX `sh`, apart from `find -mindepth`, `find -empty`, `head -c` and `date +%s`, which macOS, GNU and busybox all have (take the time from `date +%s`, not awk's `srand()`, which gives micro- or nanoseconds under mawk, Debian's and Ubuntu's default awk), and `test -O`, which dash and bash both have, and test it under `dash` as well as macOS `sh`. Keep it fast, silent, and exiting 0 on any failure, and let it write only inside its own state folder.
- **Don't add `.mcp.json`, `bin/`, `settings.json` or more hooks at the root** unless every user should get them.
- **Keep the merge gate binding everyone, its names and the workflows' hardening.** The ruleset in `.github/rulesets/main.json` lists no bypass actors: the gate binds everyone, admins included, so never add one to get a pull request through. It requires the checks `check (ubuntu-latest)`, `check (macos-latest)` and `Claude approval`, so renaming a job or matrix entry blocks every pull request until the ruleset on GitHub changes too. Pin each action to a full commit SHA with its version in a comment, give each job its own `permissions` with a comment saying why it needs each write or `id-token`, and set `persist-credentials: false` on every checkout; zizmor fails the checks otherwise. Keep the review job on the job's own `github_token`: with the Claude app's token, the action's step passes without running Claude on any pull request that changes the review workflow.
- **Keep Claude's pull request review report-only.** The review job in `.github/workflows/claude-code-review.yml` reads each pull request and comments on it, and never edits files, commits or pushes, so every change in a pull request comes from the maintainer's own Claude Code session. Keep what stops it, which `scripts/check.sh` checks. Its token: the job's only permissions are `contents: read` and `pull-requests: write`, and it passes `github_token: ${{ github.token }}`; without that input, and given `id-token: write`, the action would use the Claude app's token, which can push. Its tools: `--disallowedTools` removes Edit, Write, MultiEdit and NotebookEdit, and `--allowedTools` approves only the three `gh pr` commands and the inline-comment tool, so with no `--permission-mode`, `--dangerously-skip-permissions` or `bypassPermissions`, a headless run denies every other command that needs approval, leaving Claude Code's read-only ones. And nothing sets `use_commit_signing` or `ssh_signing_key` or allows an `mcp__github` or `mcp__github_file_ops` tool, which are there for Claude to commit, push or merge. Each pull request is reviewed by its own copy of the workflow, so this catches mistakes, not a pull request that weakens the review judging it.
- **No unit tests.** No coding agent may write a unit test or add a test framework to this project. The project is verified end to end: run the hook, skills and agents in a real Claude Code session and check what they do, and keep the pre-publish checks in `scripts/check.sh` as the only scripted checks. A test file that an eval fixture writes as the data for a case, such as a Go test double a case is about, isn't a test of this project and isn't covered.
- **Test your edits, not the installed copy.** A session working on knackpack loads the installed plugin, so the knackpack agents and skills it can start are the released version, not your edits. Test a change in a session started with `claude --plugin-dir .`, or headless with `claude -p --plugin-dir .`.
- **Run live tests on a real project in a throwaway clone.** Clone it into a scratch folder and remove the clone's remote: a project's own settings can pre-approve `git commit` and `git push` for every session started in it. In a headless run, set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, or Claude Code stops a reviewer still working in the background 10 minutes after the last turn and drops its report, and cap the spend with `--max-budget-usd`. Bring back only what generalizes, without the project's names, paths or code.

## The software-factory plugin

`plugins/software-factory/` is a second plugin in this marketplace, installed on its own. It is a mod (`hooks/register.tsx`, run by Claude Code), a Node.js helper (`helper/server.mjs`) and a plain HTML, CSS and JavaScript page (`web/`). Because the root plugin is the whole repository, its files also sit in every knackpack install, where Claude Code never loads them. The rules above about knackpack's hooks, skills and agents don't apply to it; these do.

- **Give it its own version.** Bump `plugins/software-factory/.claude-plugin/plugin.json` for any change under its folder, not knackpack's version; `scripts/check.sh` checks each plugin's version and runs `claude plugin validate` on each.
- **No comments in its code, and no dependencies.** The helper uses only Node's standard library, Node 18 or later, and the page loads nothing from outside the helper.
- **No tests in code.** Don't add `*.test.ts` or run `claude plugin test`. Test by hand in a real session started with `claude --plugin-dir plugins/software-factory` in a throwaway project: what the terminal and the page each show, a message from the page, Stop, a question and a permission prompt answered from the page and from the terminal, and that no helper is left after `/exit`, `/reload-plugins` and `kill -9` of the claude process.
- **Keep its security properties, and check them with curl after a change to the helper:**
  - no key or code in a process's arguments, in the transcript or in Claude's context;
  - only `127.0.0.1`, with `Host`, `Origin` and `Sec-Fetch-Site` checked and no CORS headers;
  - the key in a header only;
  - the CSP sent as a header, with no inline script;
  - session content rendered with `textContent`, never `innerHTML` or the like;
  - a `tool.check` hook that only answers an `ask` from the engine meant for the person, never a deny, an organization's ceiling, another plugin's ask or a classic hook's ask, holds one at a time, and offers only allow once and deny, with allow only where the page shows the whole call; the terminal row never allows.
- **Build the page from native custom elements in the light DOM, with no library, Shadow DOM or build step.** A library would be a dependency, and the CSP blocks a shadow root's `<style>`. Make something a component only when it owns state that a rebuild would destroy, such as typed text, focus or an open section, or when two places use it; plain functions and the shared classes in `app.css` cover the rest. Components take data through properties, report with bubbling `sf-…` events and never call the helper. The README's "The page's code" section lists them and gives the steps for adding one.
- **It depends on knackpack's public interface**: agent names such as `knackpack:adversarial-reviewer`, the verdict words, where intent records are kept, and the session list in the `<script id="data">` block of knackpack's software factory page, which its overview reads. When a knackpack release changes one of them, update this plugin in the same release.

## Writing and improving skills and agents

These cover what a skill or agent says and the eval cases that check it.

- **Write each description for the moment Claude chooses.** Claude decides whether to start a skill or agent from its description alone. Say what it does and which requests it's for, including ones that never use its name, then which similar requests belong elsewhere, with "Not for" and where they go instead. Name anything a user wouldn't guess, such as a long run, a large token cost or publishing. When you change a description, run a case where a realistic request should start it and one where a similar request shouldn't, such as the `trigger` cases. A skill with `disable-model-invocation: true` isn't meant to start on its own, so test the command or hook that starts it instead.
- **Give the reason with each rule.** A model that knows why a rule exists can apply it to cases nobody foresaw and can tell where it stops; an order alone, or the same order in capitals, gives it neither. When a run ignores a rule, find out why in its trace before adding emphasis: the rule may come too late in the file, read two ways, or clash with another.
- **Fix the cause, not the case.** A failed case is one example of a problem, so change the instructions until they'd handle that problem in any project, and never copy a fixture's file names, identifiers or story into a skill or agent. When a run shows a mistake the model will repeat, such as trusting a tool's surprising default, write the correction as a concrete fact at the step where it happens, not as general advice. Change a holdout case or its graders only when the case itself is wrong, and say why in the pull request: tuning against holdout cases destroys the only evidence that a fix carries over.
- **Read what the runs did, not only their scores.** A pass can be luck and a failure a broken fixture, and only the trace tells you which. Each run's `tracePath` in `aggregate-result.json` points into a temporary folder: pass `--keep-temp` to keep it, and don't run git inside the kept folder, which holds files the plugin under test wrote. Ask of each instruction whether the model would get the task wrong without it, and cut the ones that only send it on work that doesn't change the result, since every line costs tokens on every run; test a cut with the `-dev` cases. A shorter text that loses a mode boundary, an evidence requirement or where a file is saved is a regression, not a saving. When every run works out the same steps for itself, write those steps into the skill's or agent's own file. Compare cost, duration and turns with the last run as well as scores, and say in the pull request what a change adds to them.
- **Make every grader able to fail.** A grader that a wrong answer also passes gives confidence nothing earned. Check what was found, not which words appear: that a review names the failure and where it happens, not that it mentions a race. Use `tool_used` and `regex` graders where a pattern decides, and `llm` graders for judgment, each with a PASS and a FAIL condition and with anything the evidence doesn't show counted as a FAIL. In a two-arm run, a scored grader that passes in both arms measures nothing knackpack adds, unless it guards against harm, such as a publish, an edit or a finding knackpack mustn't make, as the `-kept` cases do. Keep those guards, and read them apart from the graders that measure what knackpack adds. A grader that fails in both arms is broken or asks too much. A correct answer must be able to pass, too: `llm` graders are judged by the small model Claude Code uses for background tasks unless you pass `--judge-model`, and earlier runs record it failing correct reviews, so when a run that did the job fails its grader, rerun it with `--judge-model sonnet` before changing the skill or agent, and reword a rubric that lets formatting decide.
- **Don't read much into one run.** Answers vary from run to run, and most cases set `runs: 1`, below the runner's default of 3, so a case that flips between two runs, or a score that moved by one case, may be noise. Rerun the cases a change moved with `--runs 3` or more before saying it helped or hurt.
- **Write prompts the way users ask.** A case's prompt should read like a real request, with the details a user gives, such as file names, what they need and casual wording. A case where knackpack shouldn't act tests something only when its request shares words or a topic with what knackpack does; a request nothing could mistake for one tests nothing. Nothing the agent can read should say it's being tested, whether the prompt, a file name, a comment or a commit's author, since a model that knows it's in a test may not act as it would for a user.
- **Compare versions blind.** When you judge two versions of a skill or agent by reading their outputs rather than by graders, have a fresh agent judge the outputs as A and B without telling it which version wrote which, since knowing which one is new pulls toward it.

## Before you publish

1. Run `sh scripts/check.sh` and fix whatever it reports. It runs `claude plugin validate .`, where the only expected warning is the missing icon, checks the rules in this file that a script can check, including that the version is higher than `origin/main`'s unless only files under `.github/` changed, and prints one line per check. Outside `evals/`, whose fixtures hold the defects their cases are about, it also checks for conflict markers and CRLF line endings, and that ShellCheck, actionlint, zizmor, codespell, markdownlint-cli2, lychee and gitleaks pass (each runs when installed; CI's Linux job installs them and requires all seven). Add a check there when you add a rule it can test.
2. When you add a frontmatter or hook key, confirm it in the Claude Code docs and add it to the lists in `scripts/check.sh`; Claude Code ignores a key it doesn't recognize without a word. To confirm it's applied, start `claude --debug --plugin-dir .` and search the debug log in `~/.claude/debug/` for `does not recognize or apply`.
3. Bump `version` in `.claude-plugin/plugin.json`, as Versioning below says; installed copies update only when it changes. A change only under `.github/`, such as Dependabot's, needs no bump.
4. Update the README when behavior changes, including the counts of skills, agents and eval cases. The README opens with the owner's "Engineered, Not Vibe Coded" banner, whose last line states the merge gate in `.github/rulesets/main.json`; change that line whenever the gate changes.
5. When a change affects how a skill or agent behaves, run the evals that cover it and compare the scores with the last run: `claude plugin eval . --tag quick --scaffold --allow-tools Edit`, for the adversarial reviewer `claude plugin eval . --tag reviewer --scaffold --allow-tools Bash`, for the Go reviewer `claude plugin eval . --tag go-reviewer --scaffold --allow-tools Bash`, for the Python reviewer `claude plugin eval . --tag python-dev --scaffold --allow-tools Bash` while iterating, then `--tag python-holdout` once to confirm, for the React reviewer `claude plugin eval . --tag react-dev --scaffold --allow-tools Bash` while iterating, then `--tag react-holdout` once to confirm, for the security reviewer `claude plugin eval . --tag security-dev --scaffold --allow-tools Bash "WebFetch(domain:github.com)" "WebFetch(domain:release-assets.githubusercontent.com)" "WebFetch(domain:raw.githubusercontent.com)"` while iterating, then `--tag security-holdout` with the same grants once to confirm, and `--tag security-offline --scaffold --allow-tools Bash`, with no domain granted, for its behavior when it can't download its sources, for the design pattern reviewer `claude plugin eval . --tag pattern-dev --scaffold --allow-tools Edit` while iterating, then `--tag pattern-holdout` once to confirm, and for the slop reviewer `claude plugin eval . --tag slop-dev --scaffold` while iterating, then `--tag slop-holdout` once to confirm, with `--tag slop-simplify --scaffold --allow-tools Edit Write` as the built-in `/simplify` baseline it has to beat. For the Docker, Kubernetes, Terraform and database reviewers, run `claude plugin eval . --tag docker-dev --scaffold --allow-tools Bash` (and `kubernetes-dev`, `terraform-dev`, `database-dev`) while iterating, then the matching `-holdout` tag once to confirm; for the OpenTelemetry reviewer `--tag otel-dev --scaffold --allow-tools Bash Edit`, then `otel-holdout`, granting Edit so the case that forbids edits can catch one; and for Create issues `--tag issues-dev --scaffold --allow-tools Bash Write`, then `issues-holdout`. For Write docs, run `--tag docs-dev --scaffold --allow-tools Write Edit Bash`, since the changelog case edits a file and reads the git history. Never give a Create issues case a remote it could publish to. For the challenge rules hook, run `claude plugin eval . --tag challenge --scaffold`; its cases set `EVAL_KNACKPACK_CHALLENGE`, since an eval passes only `EVAL_*` variables. For the trigger cases, which check that a realistic request starts a skill and a similar one doesn't, run `claude plugin eval . --tag trigger --scaffold --ablation none --allow-tools Edit`: without the plugin no skill can start, so the second arm would measure nothing, and five of them check that a requested edit got made, which fails without the Edit grant. In a two-arm run, graders marked `arm: with-only` (that knackpack's agent ran, its table, its verdict) are reported but not scored, so read them in the report, or add `--ablation none` to score them. Before paying for a new case, run its fixture in a scratch folder and confirm it builds and shows the problem the case is about. Evals call the model on your account, so CI doesn't run them; cap each run with `--max-cost-usd`, and when comparing with the last run, pin its model with `--model` and its judge with `--judge-model`, and name both with the results, so a model update isn't read as a change in knackpack. A case that fails after a change counts against the change only if `origin/main`'s version still passes it under the same Claude Code version, model and judge; `claude plugin eval` takes the plugin's path, so run it on a worktree of `origin/main`. Claude Code refuses Bash-granting evals on a machine whose SSH or cloud credential config uses a shell expansion it can't resolve.

## Versioning

knackpack follows [Semantic Versioning 2.0.0](https://semver.org/): `MAJOR.MINOR.PATCH`. Its public interface is what users invoke or depend on: agent and skill names, the `/knackpack:` commands, what the hooks print and where they keep files, report file names, verdict words and the findings table.

- Bump once per release, from `origin/main`'s version, however many changes it holds; `scripts/check.sh` checks that it's higher.
- While the version is `0.y.z`, which SemVer leaves for initial development, bump MINOR for a new or changed feature and for any change to the public interface, such as renaming or removing an agent, and reset PATCH to 0. Bump PATCH for fixes and rewording that change no feature or interface.
- From `1.0.0`, bump MAJOR for a change that breaks the public interface, MINOR for a feature that keeps it compatible, and PATCH for a compatible fix.
- Say in the README what a breaking change means for users and what they need to do.
