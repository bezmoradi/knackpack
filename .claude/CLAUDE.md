# Working on knackpack

knackpack is a Claude Code plugin made of Markdown plus six hook scripts and nine helper scripts: skills in `skills/<name>/SKILL.md`, agents in `agents/<name>.md` with a catalog of them for programs in `agents/catalog.json`, hooks in `hooks/` that load the track-intent skill and check that its record stays up to date, that send Claude back once at a turn's end to run checks when it edited code after its last command, that tell the developer at session start when a newer knackpack is released, with how to update and what changed from `CHANGELOG.md`, that print the challenge rules at session start, and with them, when `KNACKPACK_DOCS=repo` is set, the rules for committing the requirements brief and the plan, that warn when the context grows large, that ask each compaction's summary to keep what Claude found out itself, that, when the developer turns it on, stop a manual `/compact` until the session has a checkpoint, and that send a knackpack agent back once when its reply's verdict or findings line is missing or malformed, `scripts/commit-docs.sh`, which Claude runs to make that commit and which also commits the incident commands' `ROOT-CAUSE.md` and `INCIDENT.md`, `scripts/incident-check.sh`, which fix-incident runs to decide whether a fix may start, `scripts/repo-settings.sh`, which both source to tell whether a repository's own settings may set one of their variables, `scripts/requirements-check.sh`, which challenge-requirements runs on each requirements brief it saves and plan-implementation and execute-plan run before planning from one, `scripts/sync-protocol.sh`, which copies the review protocol into every agent, `scripts/review-scope.sh`, which every reviewer runs to resolve its review's snapshot and base the same way, `scripts/review-coverage.sh`, which orchestrate-review runs to check that every reviewer it started gave a verdict, `scripts/prompt-audit.sh`, which audits the instruction files a push changes with Claude Code's `/doctor prompt-audit`, `scripts/trigger-gate.sh`, which the prompt audit's pre-push hook runs next to check that a changed skill or agent description still starts it when it should and not when it shouldn't, the pre-publish checks in `scripts/check.sh`, which CI runs on Linux and macOS, and behavior evals in `evals/` for `claude plugin eval`. The repository root is both the plugin and its marketplace, so every file at the root ships to every user. The README's Local Development section has the commands; this file holds the rules.

## Rules

- **Edit the review protocol in one place.** All nineteen agent files end with the same "Review protocol" section, copied from `scripts/review-protocol.md`. Edit that file and run `sh scripts/sync-protocol.sh`; never edit an agent's copy, which `scripts/check.sh` reports.
- **Keep each agent's instructions in its own file.** Don't move rules into files an agent reads while it works: a plugin's files sit outside the user's project, so reading them needs permission, which Manual mode asks for and headless runs deny, and the rules would silently go missing. That includes the name of the file an agent saves its report to (`<name>.md`): a subagent never sees its own frontmatter, so its instructions have to name the file, and the review protocol asks for the name they give.
- **Keep the agents report-only.** Every agent lists its tools in `tools:` and never gets Edit, Write or NotebookEdit. Only the adversarial, security and architecture reviewers get `Agent`, and they use it only to start `knackpack:adjudicator`; Claude Code ignores a type list such as `Agent(knackpack:adjudicator)` in a subagent's `tools`, so only their instructions hold them to that. Keep `omitClaudeMd: true` on every agent.
- **Write everything yourself.** Don't copy text from other projects, even MIT-licensed ones, and don't include the text of ASVS requirements or of the other OWASP sources the security reviewer uses, which are licensed CC BY-SA; the reviewer downloads them at pinned commits instead, and checks the ASVS file's checksum. Their IDs, titles and file names are fine.
- **Keep it generic.** No company or product names from private projects, no email addresses, and no names of private repositories.
- **Check facts against primary sources:** the Claude Code docs, specs, RFCs and library source. Name the version when behavior changed in one.
- **Keep the skills in the Agent Skills format, with Claude Code's keys.** The skills use the [Agent Skills](https://agentskills.io/specification) folder format inside a Claude Code plugin, and their workflows need Claude Code's agents, hooks and variables, so nothing promises they work in other products. Say which kind of rule a change rests on. The format requires a `name` of 1 to 64 lowercase letters, digits and single hyphens between them, matching the folder, and a `description` of at most 1,024 characters, and caps `compatibility` at 500. Its documentation's advice, such as a body under 500 lines or files loaded on demand, is advice, not a requirement. Knackpack's own policy is one-line frontmatter values and Claude Code's keys `argument-hint` and `disable-model-invocation`. Keep those keys even though the format's validator, claude.ai uploads and the Skills API reject them: without `disable-model-invocation`, Claude could start on its own the plan-implementation skill, meant to start only on request, and the track-intent skill the hook already loads. `scripts/check.sh` checks all of this, since `claude plugin validate` checks only that a description exists.
- **Keep each `SKILL.md` under about 19,000 characters.** After compaction, Claude Code carries over only the first 5,000 tokens of each skill, and no more than 25,000 tokens across all the skills the session invoked, newest first, so an older skill can drop out entirely. Anything past those limits is lost, so put rules Claude must keep, such as where a skill saves its files, near the top. Keep track-intent's body under about 8,500: the hook prints it along with the session's paths, and Claude Code cuts hook output past 10,000 characters to a short preview, so past 9,900 bytes the hook prints only a pointer to the skill file, which Claude then has to read itself.
- **Keep the hooks safe for every user.** `hooks/track-intent.sh` runs at every session start, message, file edit and turn end for everyone who installs knackpack, `hooks/challenge.sh` and `hooks/update.sh` at every session start, `hooks/context.sh` at every message, `hooks/compact.sh` before every compaction, and `hooks/reply-contract.sh` whenever a subagent hands back its report through `SubagentHandback` and whenever a knackpack agent stops, headless sessions included; the rules below hold for all six, `challenge.sh`, `update.sh` and `context.sh` write nothing at all, `compact.sh` writes nothing unless `KNACKPACK_COMPACT_GATE=on` turns its gate on, and then only inside its own state folder, which it creates, keeping one empty marker per session there and deleting markers untouched for 30 days, and `reply-contract.sh` writes only when it denies a knackpack agent's hand-back for malformed reply lines, then one empty marker per agent in its own state folder, which it creates, deleting markers untouched for 30 days. Keep `reply-contract.sh` sending a reply back at most once and letting it through whenever it can't tell, so a check of the reply's format never loses a review. `track-intent.sh`'s Stop handler also checks, from the end of the session's transcript, whether the turn edited a file other than a document after the last command it ran, or ran none, and if so sends Claude back once to run the project's checks or say why there are none, in headless sessions and with `KNACKPACK_INTENT=off` too, until `KNACKPACK_TURN_CHECK=off` turns it off; it writes nothing, never asks for a commit or push, and shares the handler's one send-back per stop, so a Stop prints at most one JSON object, since Claude Code ignores output holding two. Keep it POSIX `sh`, apart from `find -mindepth`, `find -empty`, `head -c` and `date +%s`, which macOS, GNU and busybox all have (take the time from `date +%s`, not awk's `srand()`, which gives micro- or nanoseconds under mawk, Debian's and Ubuntu's default awk), and `test -O`, which dash and bash both have, and test it under `dash` as well as macOS `sh`. Keep it fast, silent, and exiting 0 on any failure, and let it write only inside its own state folder. The one exit that isn't 0 is the gate's deliberate exit 2, which stops a manual `/compact` in an attended session; keep every doubt letting the compaction through.
- **Keep `hooks/update.sh` the only hook that uses the network, and keep its one request.** Claude Code doesn't auto-update third-party marketplaces by default, and with that off the marketplace's copy on disk is never refreshed, so the only way to tell a user about a release is to ask GitHub; the developer chose a check at every session start over a cached daily one. Keep it to one HTTPS GET of `CHANGELOG.md` from this repository's `main` on `raw.githubusercontent.com`, with nothing about the user or their project in the request, at most 3 seconds, and no retry, cache or file written. Keep it skipped after a compaction, in headless sessions, and when `KNACKPACK_UPDATE_CHECK=off` or Claude Code's `DISABLE_UPDATES`, `DISABLE_AUTOUPDATER` or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set, since those are how a user or an organization turns update traffic off. What it fetches is text from the network: never run it, strip its control characters, cap it, and hand it to Claude only as data to summarize. Its notice reaches the developer twice, as `systemMessage`, which Claude Code 2.1.329 shows at session start, and in Claude's first reply.
- **Keep `scripts/commit-docs.sh` committing only what it's given.** Claude runs it to commit, never a hook, and only when `KNACKPACK_DOCS=repo` asks for it, which the script checks too; `hooks/challenge.sh` runs only its read-only `--check`, before printing the rules. Keep it refusing when the repository's own settings may set that variable, a `.claude/settings.json` in the folder or above it, or any `.claude/settings.json` or `.claude/settings.local.json` git tracks, that names it or uses a `\u` escape, which JSON allows for any letter of a key, so a repository can't switch the mode on for someone who didn't choose it. It writes into the user's repository by design, so keep it to the same shells and portable commands as the hooks. Keep it committing exactly the one document under `.knackpack/` and `.knackpack/feature.json`, from an index of its own made from HEAD (`GIT_INDEX_FILE`), so the user's index and other staged and unstaged work aren't touched before the commit is checked. A repository's commit hooks can still stage more or change the text, so keep it checking what the commit holds and taking the commit back when it holds anything else. Keep it refusing a document that names a path from the machine, refusing during a merge, cherry-pick, revert or rebase, and putting `feature.json` back when it doesn't commit. `scripts/check.sh` runs it in a throwaway repository, including with a failing commit hook, with one that stages other work, and with the variable in the repository's settings, spelled plainly and with an escape.
- **Keep `scripts/incident-check.sh` read-only and refusing by default.** fix-incident runs it before changing any code, so it prints one line, `approved <sha256>`, `ask <sha256>` or `refused: <reason>`, writes nothing, and refuses a diagnosis that is missing, isn't `CONFIRMED`, or, with `KNACKPACK_DOCS=repo`, isn't committed or differs from its committed text. It accepts `KNACKPACK_INCIDENT_APPROVED_SHA256` only when it matches the hash and the repository's own settings can't have set it, the same rule `commit-docs.sh` keeps for `KNACKPACK_DOCS`, and refuses a headless run with no hash, since no one there can approve. Like `commit-docs.sh`, it's a check for an agent that follows the rules, not a security boundary, and the docs must say so. `scripts/check.sh` runs it in a throwaway repository under every shell.
- **Keep `scripts/requirements-check.sh` read-only, one pass, and the reference reader of its format.** Plan-implementation and execute-plan run it before planning from a requirements brief, and challenge-requirements after saving one, so it prints one line, `ready`, `blocked <IDs>`, `invalid: <reason>`, `none` or `error: <reason>`, exiting 0 to 4, reads only the file it's given, writes nothing, and never fails or loops on any input. The format's rules are written in `docs/requirements-format.md`. A program that reads a brief must reach the same result from the same text, so those rules, and the script that applies them, change only with a new format version, `knackpack-requirements/2`, and the script, that file and the README's summary of the format change together. Keep the checked rules to the two the format has, an `Acceptance:` line for each requirement and `Blocking: yes` or `Blocking: no` on each question: every rule added is one more that every brief and every other reader has to meet. Like `commit-docs.sh`, it's a check for an agent that follows the rules, not a security boundary, and the docs must say so. Keep it to the same shells and portable commands as the hooks; `scripts/check.sh` runs it under every shell.
- **Keep the prompt audit and the trigger gate on the maintainer's machine, and let them stop a push.** `scripts/prompt-audit.sh` runs Claude Code's `/doctor prompt-audit` (2.1.283 or later) headless on each `SKILL.md`, agent, `.claude/CLAUDE.md` and `scripts/review-protocol.md` that a commit changes since `origin/main`, as committed, in a temporary worktree, and fails while a finding the audit rates high-confidence stands; `sh scripts/prompt-audit.sh --install` makes it this clone's pre-push hook, which the maintainer chose to block rather than warn. Each file it audits is a model run on the maintainer's account, about $1 to $2 and a minute or two, so never run it from CI or a plugin hook. It keeps each file version's result in the git folder and doesn't audit it again, because the verdict varies from run to run and rerunning until it passes would make the check meaningless. When it blocks, fix the finding and commit; `--accept <path>` and `git push --no-verify` are the maintainer's to use, never Claude's on its own judgment, since the gate exists to stop what Claude thinks is fine. A finding that rewords a skill or agent is still a change to its behavior, so run its evals before and after, as below. When Claude pushes, run the push in the background, since auditing many files takes longer than a Bash call's 10-minute limit and the push would be cut off mid-audit. git connects to the remote before it runs the hook, so a long audit can outlast that connection and the push then fails after the audit passed; push again, which reuses the saved results and costs nothing. When the audit passes, the same hook runs `scripts/trigger-gate.sh`, which costs nothing unless the push changes a skill's or agent's `description:` line. For each one it does change, it runs that component's `trigger` cases tagged `"starts:knackpack:<name>"` or `"quiet:knackpack:<name>"` with `claude plugin eval`, taking the cases from `origin/main` so a change can't tune its own test, on the merge base and on the commit, and it blocks when the share of runs that start where they should, or stay quiet where they should, drops, and when no such case measures the component. That is each case's cost twice, $0.16 to $0.63 a run in the runs recorded so far, more for a case that starts a whole review, capped by `KNACKPACK_TRIGGER_BUDGET` (default $5) for each commit it gates, so like the audit it never runs from CI or a plugin hook. It keeps results per description version the same way, so `KNACKPACK_TRIGGER_RUNS=3`, which measures afresh, is the way to a second look at a result one run may have tipped, and `--accept <component>` is the maintainer's alone, as above. `prompt-audit.sh --hook` runs the gate itself once the audit passes, so the hook `sh scripts/prompt-audit.sh --install` writes stays one line that hands over to it, and a check added later reaches every installed hook with a pull; keep new pre-push checks in `--hook`, never in the hook's text. The repository's own `.claude/settings.json` runs `--ensure` at session start, which installs that hook, or updates knackpack's own older one, only in a clone whose `origin` is github.com/bezmoradi/knackpack, since the hook spends on the account of whoever pushes and only the maintainer pushes there, and never touches a pre-push hook that isn't knackpack's. Claude Code reads that file as settings for working on this repository, not from an installed plugin, so it's not one of the plugin's hooks.
- **Don't add `.mcp.json`, `bin/`, `settings.json` or more hooks at the root** unless every user should get them.
- **Keep the merge gate binding everyone, its names and the workflows' hardening.** The ruleset in `.github/rulesets/main.json` lists no bypass actors: the gate binds everyone, admins included, so never add one to get a pull request through. The one way past Claude's verdict is the `skip-claude-approval` label, which the `Claude approval` job reads from the pull request when it runs; only the maintainer adds it, when they judge the review's findings wrong or not worth fixing, and Claude never adds it on its own judgment. It requires the checks `check (ubuntu-latest)`, `check (macos-latest)`, `Claude review` and `Claude approval`, so renaming a job or matrix entry blocks every pull request until the ruleset on GitHub changes too. Pin each action to a full commit SHA with its version in a comment, give each job its own `permissions` with a comment saying why it needs each write or `id-token`, and set `persist-credentials: false` on every checkout; zizmor fails the checks otherwise. Keep the review job on the job's own `github_token`: with the Claude app's token, the action's step passes without running Claude on any pull request that changes the review workflow.
- **Keep Claude's pull request review report-only.** The review job in `.github/workflows/claude-code-review.yml` reads each pull request and comments on it, and never edits files, commits or pushes, so every change in a pull request comes from the maintainer's own Claude Code session. Keep what stops it, which `scripts/check.sh` checks. Its token: the job's only permissions are `contents: read` and `pull-requests: write`, and it passes `github_token: ${{ github.token }}`; without that input, and given `id-token: write`, the action would use the Claude app's token, which can push. Its tools: `--disallowedTools` removes Edit, Write, MultiEdit and NotebookEdit, and `--allowedTools` approves only the three `gh pr` commands and the inline-comment tool, so with no `--permission-mode`, `--dangerously-skip-permissions` or `bypassPermissions`, a headless run denies every other command that needs approval, leaving Claude Code's read-only ones. And nothing sets `use_commit_signing` or `ssh_signing_key` or allows an `mcp__github` or `mcp__github_file_ops` tool, which are there for Claude to commit, push or merge. Each pull request is reviewed by its own copy of the workflow, so this catches mistakes, not a pull request that weakens the review judging it.
- **No unit tests.** No coding agent may write a unit test or add a test framework to this project. The project is verified end to end: run the hook, skills and agents in a real Claude Code session and check what they do, and keep the pre-publish checks in `scripts/check.sh` as the only scripted checks. A test file that an eval fixture writes as the data for a case, such as a Go test double a case is about, isn't a test of this project and isn't covered. Nor is `evals/consistency.sh`, which reads eval results and reports how consistent repeated runs were: it's an analysis tool for the maintainer, not a pre-publish check, tests nothing in the project and isn't run by CI, so `scripts/check.sh` still holds the only scripted checks.
- **Test your edits, not the installed copy.** A session working on knackpack loads the installed plugin, so the knackpack agents and skills it can start are the released version, not your edits. Test a change in a session started with `claude --plugin-dir .`, or headless with `claude -p --plugin-dir .`.
- **Run live tests on a real project in a throwaway clone.** Clone it into a scratch folder and remove the clone's remote: a project's own settings can pre-approve `git commit` and `git push` for every session started in it. In a headless run, set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` (Claude Code 2.1.182 or later), or Claude Code stops a reviewer still working in the background 10 minutes after the last turn and drops its report, and cap the spend with `--max-budget-usd`. Bring back only what generalizes, without the project's names, paths or code.

## Tools that read knackpack's interface

An outside tool will read part of knackpack's public interface when knackpack is installed: agent names such as `knackpack:adversarial-reviewer` and `knackpack:slop-reviewer`, the verdict words its push gate will read, the `knackpack-verdict/1:` line every reviewer's reply ends with, which the gate reads first, the `knackpack-findings/1:` line just before it in every reply but the adjudicator's, which counts the findings table's rows by severity and those that block, the `knackpack-finding/1` lines before that, one for each of the table's first 200 rows and none for an empty table, the `knackpack-coverage/1` lines before those, one for each requirement ID a reviewer was given, up to 100, and none when it was given none, both kinds in the same form whether the count command printed them or a reviewer that can't run it wrote them itself, the reviewer catalog `agents/catalog.json` with its `knackpack-catalog/1` format, where intent records are kept and the Files line they list, with its paths separated by `, `, where plan-implementation saves `PLAN.md`, the incident commands' `ROOT-CAUSE.md` and `INCIDENT.md`, their headings, ROOT-CAUSE.md's Status words and the `KNACKPACK_INCIDENT_APPROVED_SHA256` variable fix-incident reads, the requirements brief's `knackpack-requirements/1` marker line, its headings `### Requirements and acceptance criteria` and `### Open questions and risks`, its `#### <ID>: <text>` requirement headings with their `Acceptance:` lines and its `- Q-<n>: <text> Blocking: yes` or `Blocking: no` question lines, and `scripts/requirements-check.sh`'s output lines, `ready`, `blocked <IDs>`, `invalid: <reason>`, `none` and `error: <reason>`, with their exit codes 0 to 4, and, with `KNACKPACK_DOCS=repo`, the committed copies at `.knackpack/<task>/REQUIREMENTS.md`, `.knackpack/<task>/PLAN.md`, `.knackpack/<task>/ROOT-CAUSE.md` and `.knackpack/<task>/INCIDENT.md` and `.knackpack/feature.json`, which names the current task's folder as `{"feature_directory": ".knackpack/<task>"}`. A change to any of them would break its push gate or intent panel, so name it as a breaking change in `CHANGELOG.md`. The changelog's own headings, `## <version> (<date>)` with the newest first, are public interface too, though nothing outside reads them: every installed copy's update hook parses the newest changelog to find the latest version and what changed, so a different heading would silently end the notice for everyone on an older version.

## Writing and improving skills and agents

These cover what a skill or agent says and the eval cases that check it.

- **Write each description for the moment Claude chooses.** Claude decides whether to start a skill or agent from its description alone. Say what it does and which requests it's for, including ones that never use its name, then which similar requests belong elsewhere, with "Not for" and where they go instead. Name anything a user wouldn't guess, such as a long run, a large token cost or publishing. When you change a description, run a case where a realistic request should start it and one where a similar request shouldn't, such as the `trigger` cases. Tag each case that checks this `"starts:knackpack:<name>"` or `"quiet:knackpack:<name>"`, quoted, since libyaml can't read the colons unquoted, and give it a `tool_used` or `tool_order` grader on the Skill or Agent tool that names the component, with `max: 0` for quiet. `scripts/check.sh` requires one of each for every agent and every skill Claude may start, apart from those in `evals/trigger-gaps.txt`, a list that may only shrink, and the pre-push hook runs a changed description's `trigger` cases, as above. A skill with `disable-model-invocation: true` isn't meant to start on its own, so test the command or hook that starts it instead.
- **Give the reason with each rule.** A model that knows why a rule exists can apply it to cases nobody foresaw and can tell where it stops; an order alone, or the same order in capitals, gives it neither. When a run ignores a rule, find out why in its trace before adding emphasis: the rule may come too late in the file, read two ways, or clash with another.
- **Fix the cause, not the case.** A failed case is one example of a problem, so change the instructions until they'd handle that problem in any project, and never copy a fixture's file names, identifiers or story into a skill or agent. When a run shows a mistake the model will repeat, such as trusting a tool's surprising default, write the correction as a concrete fact at the step where it happens, not as general advice. Change a holdout case or its graders only when the case itself is wrong, and say why in the pull request: tuning against holdout cases destroys the only evidence that a fix carries over.
- **Read what the runs did, not only their scores.** A pass can be luck and a failure a broken fixture, and only the trace tells you which. Each run's `tracePath` in `aggregate-result.json` points into a temporary folder: pass `--keep-temp` to keep it, and don't run git inside the kept folder, which holds files the plugin under test wrote. Ask of each instruction whether the model would get the task wrong without it, and cut the ones that only send it on work that doesn't change the result, since every line costs tokens on every run; test a cut with the `-dev` cases. A shorter text that loses a mode boundary, an evidence requirement or where a file is saved is a regression, not a saving. When every run works out the same steps for itself, write those steps into the skill's or agent's own file. Compare cost, duration and turns with the last run as well as scores, and say in the pull request what a change adds to them.
- **Make every grader able to fail.** A grader that a wrong answer also passes gives confidence nothing earned. Check what was found, not which words appear: that a review names the failure and where it happens, not that it mentions a race. Use `tool_used` and `regex` graders where a pattern decides, and `llm` graders for judgment, each with a PASS and a FAIL condition and with anything the evidence doesn't show counted as a FAIL. Give each `llm` grader one question, and when a case needs several things checked, give each its own grader, leaving to a `tool_used` or `regex` grader what one can check: a rubric that asks for several things lets the judge fail a correct answer over the least of them, and its failure doesn't say which was missing. In a two-arm run, a scored grader that passes in both arms measures nothing knackpack adds, unless it guards against harm, such as a publish, an edit or a finding knackpack mustn't make, as the `-kept` cases do. Keep those guards, and read them apart from the graders that measure what knackpack adds. A grader that fails in both arms is broken or asks too much. A correct answer must be able to pass, too: `llm` graders are judged by the small model Claude Code uses for background tasks unless you pass `--judge-model`, and earlier runs record it failing correct reviews, so when a run that did the job fails its grader, rerun it with `--judge-model sonnet` before changing the skill or agent, and reword a rubric that lets formatting decide.
- **Don't read much into one run.** Answers vary from run to run, and most cases set `runs: 1`, below the runner's default of 3, so a case that flips between two runs, or a score that moved by one case, may be noise. Rerun the cases a change moved with `--runs 3` or more before saying it helped or hurt.
- **Write prompts the way users ask.** A case's prompt should read like a real request, with the details a user gives, such as file names, what they need and casual wording. A case where knackpack shouldn't act tests something only when its request shares words or a topic with what knackpack does; a request nothing could mistake for one tests nothing. Nothing the agent can read should say it's being tested, whether the prompt, a file name, a comment or a commit's author, since a model that knows it's in a test may not act as it would for a user.
- **Compare versions blind.** When you judge two versions of a skill or agent by reading their outputs rather than by graders, have a fresh agent judge the outputs as A and B without telling it which version wrote which, since knowing which one is new pulls toward it.

## Before you publish

1. Run `sh scripts/check.sh` and fix whatever it reports. It runs `claude plugin validate .`, where the only expected warning is the missing icon, checks the rules in this file that a script can check, including that the version is higher than `origin/main`'s unless only files under `.github/` changed, and prints one line per check. Outside `evals/`, whose fixtures hold the defects their cases are about, it also checks for conflict markers and CRLF line endings, and that ShellCheck, actionlint, zizmor, codespell, markdownlint-cli2, lychee and gitleaks pass (each runs when installed; CI's Linux job installs them and requires all seven). Add a check there when you add a rule it can test.
2. When you add a frontmatter or hook key, confirm it in the Claude Code docs and add it to the lists in `scripts/check.sh`; Claude Code ignores a key it doesn't recognize without a word. To confirm it's applied, start `claude --debug --plugin-dir .` and search the debug log in `~/.claude/debug/` for `does not recognize or apply`.
3. Bump `version` in `.claude-plugin/plugin.json`, as Versioning below says; installed copies update only when it changes. A change only under `.github/`, such as Dependabot's, needs no bump. Add the version's entry at the top of `CHANGELOG.md`, written for the users who will read Claude's summary of it: what changes for them, with **Breaking:** before each change that breaks the public interface and what they need to do. `scripts/check.sh` checks that the newest heading is the version in `plugin.json`.
4. Update the README when behavior changes, including the counts of skills, agents and eval cases. The README opens with the owner's "Engineered, Not Vibe Coded" banner, worded the same in all of the owner's open-source repositories; leave its wording as the owner set it, even where it doesn't describe this repository's merge gate.
5. When a change affects how a skill or agent behaves, run the evals that cover it and compare the scores with the last run. Each command is `claude plugin eval . --tag <tag> --scaffold` followed by the row's grants as `--allow-tools`. Where a row names two tags, run the first while iterating, then the `-holdout` tag once, with the same grants, to confirm.    Never give a Create issues case a remote it could publish to. The incident and `plan-brief` cases run with `--ablation none` too, since they start commands that exist only with the plugin. The trigger cases run with `--ablation none` because without the plugin no skill can start, so the second arm would measure nothing, and those that check that a requested edit got made fail without the Edit grant. The `consistency` cases, each also tagged with the failure mode it covers (`mode:alignment` and so on), measure whether knackpack gives the same answer every time, which a run without it can't show, so they run with `--ablation none`, and with `--keep-temp`, since the verdicts and findings are read from the traces. Run them on a worktree of `origin/main` and on the change, then compare the two result folders with `sh evals/consistency.sh <base> <candidate>`, which prints pass^N, verdicts and findings that differ between runs, cases that flipped, and, apart from every count, each failed grader in a case tagged `severe`. No case covers the context hook: a case that resumes a conversation through `context.history_file` starts a new session whose transcript gets the conversation's token counts only after the hook has read it, and the runner writes that transcript into the case's folder. No case covers the compaction hook either: only a compaction reads what it prints, so `scripts/check.sh` tests that text, and a headless `/compact` in a resumed throwaway session, with a PostCompact hook saving `compact_summary`, shows it reaching the summary. No case covers the update hook: it reads the changelog from GitHub, where an eval can't put an older or newer one, so `scripts/check.sh` runs it on changelogs of its own with `--from <file>`.

   In a two-arm run, graders marked `arm: with-only` (that knackpack's agent ran, its table, its verdict) are reported but not scored, so read them in the report, or add `--ablation none` to score them. Before paying for a new case, run its fixture in a scratch folder and confirm it builds and shows the problem the case is about. Evals call the model on your account, so CI doesn't run them; cap each run with `--max-cost-usd`, and when comparing with the last run, pin its model with `--model` and its judge with `--judge-model`, and name both with the results, so a model update isn't read as a change in knackpack. A case that fails after a change counts against the change only if `origin/main`'s version still passes it under the same Claude Code version, model and judge; `claude plugin eval` takes the plugin's path, so run it on a worktree of `origin/main`. Claude Code refuses Bash-granting evals on a machine whose SSH or cloud credential config uses a shell expansion it can't resolve.

## Versioning

knackpack follows [Semantic Versioning 2.0.0](https://semver.org/): `MAJOR.MINOR.PATCH`. Its public interface is what users invoke or depend on: agent and skill names, the `/knackpack:` commands, what the hooks print and where they keep files, report file names, verdict words and the findings table.

- Bump once per release, from `origin/main`'s version, however many changes it holds; `scripts/check.sh` checks that it's higher.
- While the version is `0.y.z`, which SemVer leaves for initial development, bump MINOR for a new or changed feature and for any change to the public interface, such as renaming or removing an agent, and reset PATCH to 0. Bump PATCH for fixes and rewording that change no feature or interface.
- From `1.0.0`, bump MAJOR for a change that breaks the public interface, MINOR for a feature that keeps it compatible, and PATCH for a compatible fix.
- Say in the README and in `CHANGELOG.md` what a breaking change means for users and what they need to do.
