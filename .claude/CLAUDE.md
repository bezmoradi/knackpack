# Working on knackpack

knackpack is a Claude Code plugin made of Markdown plus one hook: skills in `skills/<name>/SKILL.md`, agents in `agents/<name>.md`, hooks in `hooks/` that load the track-intent skill and check that its record stays up to date, the pre-publish checks in `scripts/check.sh`, which CI runs on Linux and macOS, and behavior evals in `evals/` for `claude plugin eval`. The repository root is both the plugin and its marketplace, so every file at the root ships to every user. The README's Local Development section has the commands; this file holds the rules.

## Rules

- **Edit the review protocol in one place.** All thirteen agent files end with the same "Review protocol" section, copied from `scripts/review-protocol.md`. Edit that file and run `sh scripts/sync-protocol.sh`; never edit an agent's copy, which `scripts/check.sh` reports.
- **Keep each agent's instructions in its own file.** Don't move rules into files an agent reads while it works: a plugin's files sit outside the user's project, so reading them needs permission, which Manual mode asks for and headless runs deny, and the rules would silently go missing. That includes the name of the file an agent saves its report to (`<name>.md`): a subagent never sees its own frontmatter, so its instructions have to name the file, and the review protocol asks for the name they give.
- **Keep the agents report-only.** Every agent lists its tools in `tools:` and never gets Edit, Write or NotebookEdit. Only the adversarial, security and architecture reviewers get `Agent`, and they use it only to start `knackpack:adjudicator`; Claude Code ignores a type list such as `Agent(knackpack:adjudicator)` in a subagent's `tools`, so only their instructions hold them to that. Keep `omitClaudeMd: true` on every agent.
- **Write everything yourself.** Don't copy text from other projects, even MIT-licensed ones, and don't include the text of ASVS requirements or of the other OWASP sources the security reviewer uses, which are licensed CC BY-SA; the reviewer downloads them at pinned commits instead, and checks the ASVS file's checksum. Their IDs, titles and file names are fine.
- **Keep it generic.** No company or product names from private projects, no email addresses, and no names of private repositories.
- **Check facts against primary sources:** the Claude Code docs, specs, RFCs and library source. Name the version when behavior changed in one.
- **Keep each `SKILL.md` under about 19,000 characters.** After compaction, Claude Code carries over only the first 5,000 tokens of each skill, and anything past that is lost, so put rules Claude must keep, such as where a skill saves its files, near the top. Keep track-intent's body under about 8,500: the hook prints it along with the session's paths, and Claude Code cuts hook output past 10,000 characters to a short preview, so past 9,900 bytes the hook prints only a pointer to the skill file, which Claude then has to read itself.
- **Keep the hook safe for every user.** `hooks/track-intent.sh` runs at every session start, message, file edit and turn end for everyone who installs knackpack. Keep it POSIX `sh`, apart from `find -mindepth`, `find -empty` and `head -c`, which macOS, GNU and busybox all have, and `test -O`, which dash and bash both have, and test it under `dash` as well as macOS `sh`. Keep it fast, silent, and exiting 0 on any failure, and let it write only inside its own state folder.
- **Don't add `.mcp.json`, `bin/`, `settings.json` or more hooks at the root** unless every user should get them.
- **Keep the merge gate binding everyone, its names and the workflows' hardening.** The ruleset in `.github/rulesets/main.json` lists no bypass actors: the gate binds everyone, admins included, so never add one to get a pull request through. It requires the checks `check (ubuntu-latest)`, `check (macos-latest)` and `Claude approval`, so renaming a job or matrix entry blocks every pull request until the ruleset on GitHub changes too. Pin each action to a full commit SHA with its version in a comment, give each job its own `permissions` with a comment saying why it needs each write or `id-token`, and set `persist-credentials: false` on every checkout; zizmor fails the checks otherwise. Keep the review job on the job's own `github_token`: with the Claude app's token, the action's step passes without running Claude on any pull request that changes the review workflow.
- **Keep Claude's pull request review report-only.** The review job in `.github/workflows/claude-code-review.yml` reads each pull request and comments on it, and never edits files, commits or pushes, so every change in a pull request comes from the maintainer's own Claude Code session. Keep what stops it, which `scripts/check.sh` checks. Its token: the job's only permissions are `contents: read` and `pull-requests: write`, and it passes `github_token: ${{ github.token }}`; without that input, and given `id-token: write`, the action would use the Claude app's token, which can push. Its tools: `--disallowedTools` removes Edit, Write, MultiEdit and NotebookEdit, and `--allowedTools` approves only the three `gh pr` commands and the inline-comment tool, so with no `--permission-mode`, `--dangerously-skip-permissions` or `bypassPermissions`, a headless run denies every other command that needs approval, leaving Claude Code's read-only ones. And nothing sets `use_commit_signing` or `ssh_signing_key` or allows an `mcp__github` or `mcp__github_file_ops` tool, which are there for Claude to commit, push or merge. Each pull request is reviewed by its own copy of the workflow, so this catches mistakes, not a pull request that weakens the review judging it.
- **No unit tests.** No coding agent may write a unit test or add a test framework to this project. The project is verified end to end: run the hook, skills and agents in a real Claude Code session and check what they do, and keep the pre-publish checks in `scripts/check.sh` as the only scripted checks. A test file that an eval fixture writes as the data for a case, such as a Go test double a case is about, isn't a test of this project and isn't covered.
- **Test your edits, not the installed copy.** A session working on knackpack loads the installed plugin, so the knackpack agents and skills it can start are the released version, not your edits. Test a change in a session started with `claude --plugin-dir .`, or headless with `claude -p --plugin-dir .`.
- **Run live tests on a real project in a throwaway clone.** Clone it into a scratch folder and remove the clone's remote: a project's own settings can pre-approve `git commit` and `git push` for every session started in it. In a headless run, set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, or Claude Code stops a reviewer still working in the background 10 minutes after the last turn and drops its report, and cap the spend with `--max-budget-usd`. Bring back only what generalizes, without the project's names, paths or code.

## Before you publish

1. Run `sh scripts/check.sh` and fix whatever it reports. It runs `claude plugin validate .`, where the only expected warning is the missing icon, checks the rules in this file that a script can check, including that the version is higher than `origin/main`'s unless only files under `.github/` changed, and prints one line per check. Outside `evals/`, whose fixtures hold the defects their cases are about, it also checks for conflict markers and CRLF line endings, and that ShellCheck, actionlint, zizmor, codespell, markdownlint-cli2, lychee and gitleaks pass (each runs when installed; CI's Linux job installs them and requires all seven). Add a check there when you add a rule it can test.
2. When you add a frontmatter or hook key, confirm it in the Claude Code docs and add it to the lists in `scripts/check.sh`; Claude Code ignores a key it doesn't recognize without a word. To confirm it's applied, start `claude --debug --plugin-dir .` and search the debug log in `~/.claude/debug/` for `does not recognize or apply`.
3. Bump `version` in `.claude-plugin/plugin.json`, as Versioning below says; installed copies update only when it changes. A change only under `.github/`, such as Dependabot's, needs no bump.
4. Update the README when behavior changes, including the counts of skills, agents and eval cases.
5. When a change affects how a skill or agent behaves, run the evals that cover it and compare the scores with the last run: `claude plugin eval . --tag quick --scaffold --allow-tools Edit`, for the adversarial reviewer `claude plugin eval . --tag reviewer --scaffold --allow-tools Bash`, for the Go reviewer `claude plugin eval . --tag go-reviewer --scaffold --allow-tools Bash`, for the Python reviewer `claude plugin eval . --tag python-dev --scaffold --allow-tools Bash` while iterating, then `--tag python-holdout` once to confirm, for the security reviewer `claude plugin eval . --tag security-dev --scaffold --allow-tools Bash "WebFetch(domain:github.com)" "WebFetch(domain:release-assets.githubusercontent.com)" "WebFetch(domain:raw.githubusercontent.com)"` while iterating, then `--tag security-holdout` with the same grants once to confirm, and `--tag security-offline --scaffold --allow-tools Bash`, with no domain granted, for its behavior when it can't download its sources, for the design pattern reviewer `claude plugin eval . --tag pattern-dev --scaffold --allow-tools Edit` while iterating, then `--tag pattern-holdout` once to confirm, and for the slop reviewer `claude plugin eval . --tag slop-dev --scaffold` while iterating, then `--tag slop-holdout` once to confirm, with `--tag slop-simplify --scaffold --allow-tools Edit Write` as the built-in `/simplify` baseline it has to beat. For the Docker, Kubernetes, Terraform and database reviewers, run `claude plugin eval . --tag docker-dev --scaffold --allow-tools Bash` (and `kubernetes-dev`, `terraform-dev`, `database-dev`) while iterating, then the matching `-holdout` tag once to confirm; for the OpenTelemetry skill `--tag otel-dev --scaffold --allow-tools Edit`, then `otel-holdout`; and for Create issues `--tag issues-dev --scaffold --allow-tools Bash Write`, then `issues-holdout`. Never give a Create issues case a remote it could publish to. In a two-arm run, graders marked `arm: with-only` (that knackpack's agent ran, its table, its verdict) are reported but not scored, so read them in the report, or add `--ablation none` to score them. Before paying for a new case, run its fixture in a scratch folder and confirm it builds and shows the problem the case is about. Evals call the model on your account, so CI doesn't run them, and Claude Code refuses Bash-granting evals on a machine whose SSH or cloud credential config uses a shell expansion it can't resolve.

## Versioning

knackpack follows [Semantic Versioning 2.0.0](https://semver.org/): `MAJOR.MINOR.PATCH`. Its public interface is what users invoke or depend on: agent and skill names, the `/knackpack:` commands, what the hooks print and where they keep files, report file names, verdict words and the findings table.

- Bump once per release, from `origin/main`'s version, however many changes it holds; `scripts/check.sh` checks that it's higher.
- While the version is `0.y.z`, which SemVer leaves for initial development, bump MINOR for a new or changed feature and for any change to the public interface, such as renaming or removing an agent, and reset PATCH to 0. Bump PATCH for fixes and rewording that change no feature or interface.
- From `1.0.0`, bump MAJOR for a change that breaks the public interface, MINOR for a feature that keeps it compatible, and PATCH for a compatible fix.
- Say in the README what a breaking change means for users and what they need to do.
